## 2026/08/23 09:42:49

### 使用者

所的稅扣繳跟最低工資等法規文字  ??

### 助理

對，這兩塊我剛剛再查後，有一個重要修正：**「所得稅扣繳」其實比我前面說的更適合自動化；「最低工資／勞基法文字規則」則是另一種類型。**

### 所得稅扣繳：可以自動化程度很高

財政部在政府資料開放平台上真的有「薪資所得扣繳稅額表」資料集，而且不是只有 PDF。官方資料集直接提供 CSV，欄位包括「每月薪資所得」以及配偶＋受扶養親屬 0～11 人各自的應扣稅額；更新頻率標示為每年一次。citeturn0search12

例如我們 Payroll 可以：

```text
員工當月薪資
      +
員工扣繳方式
      +
配偶／扶養親屬資料
      ↓
當年度薪資所得扣繳稅額表
      ↓
應扣所得稅
```

另外財政部也明確規定，居住者的按月薪資可以選擇依「薪資所得扣繳稅額表」或按全月給付總額 5% 扣繳；非每月給付的獎金、津貼等又有不同規則，非居住者也有另外的扣繳規則。citeturn0search7turn0search8

所以我們未來還需要一個**員工稅務設定**：

```text
員工
└─ 稅務／扣繳設定
   ├─ 居住者／非居住者
   ├─ 扣繳方式
   ├─ 配偶
   ├─ 扶養親屬人數
   └─ 生效歷史
```

這一塊之前我們還沒有設計到。

而且財政部目前也有 115 年度（2026）薪資所得扣繳稅額表，並保留歷年度資料。citeturn0search0turn0search1

---

### 最低工資／勞基法規則：不能跟級距表用同一套思維

這類東西比較像：

```text
政府法條／公告
        ↓
系統計算規則
```

例如：

```text
最低工資
正常工時
延長工時
休息日加班
例假日
國定假日
特休未休工資
平均工資
```

它們不是單純：

> 政府給一張 CSV → 我們查表。

而是政府規定**計算邏輯與適用條件**。

所以我不建議系統：

```text
抓法規文字
↓
AI 看懂
↓
自動修改 Payroll 公式    ❌
```

薪資系統這樣做風險太高。

應該是：

```text
政府法規／公告
      ↓
偵測有沒有變更
      ↓
通知系統管理員
      ↓
人工確認規則變更
      ↓
程式更新／規則版本更新
      ↓
測試
      ↓
正式生效
```

---

### 所以我們的「法規模組」其實應該分兩類

```text
法規設定
│
├─ A. 政府結構化計算資料
│  ├─ 勞保級距
│  ├─ 勞就保分擔表
│  ├─ 健保級距
│  ├─ 勞退級距
│  ├─ 職災級距／費率
│  └─ 薪資所得扣繳稅額表
│
│     → 可以自動同步
│     → 保存歷史版本
│     → Payroll 直接使用
│
└─ B. 法規計算邏輯
   ├─ 最低工資
   ├─ 工時
   ├─ 加班
   ├─ 休息日
   ├─ 例假
   ├─ 國定假日
   ├─ 特休
   └─ 平均工資等

         → 追蹤政府法規
         → 偵測異動
         → 人工確認
         → 發布新的計算規則版本
```

這個分界我認為非常重要。

**政府有「數據」的，我們自動同步；政府提供的是「法律規則」的，我們追蹤變更，但不能讓系統看到法條變了就自行改 Payroll 演算法。**

這樣我們現在的法規 Schema 也應該跟著調整，而不是把兩種資料都塞進同一個 `regulatory_records`。

### 使用者

我們不用管員工稅務吧，我們不是已經有設定扶養??這樣在計算工資時，如果超過規定，我們不是就可以計算要扣多少所得稅?

### 助理

對，你的方向基本上是對的。**如果我們前面的人事資料已經有「配偶／扶養親屬」資料，就沒必要再做一套重複的「員工稅務資料」。**

但有一個小地方需要補：**扣繳方式**。

財政部目前規定，境內居住者的每月薪資扣繳，可以由員工選擇：

- 依「薪資所得扣繳稅額表」計算
- 或按全月薪資 **5%** 扣繳

而採稅額表時，確實會依「薪資金額 + 配偶及受扶養親屬人數」查出應扣稅額。citeturn0search0turn0search1

所以我們可以這樣設計：

```text
員工
│
├─ 配偶資料                 ← 已有
├─ 扶養親屬                 ← 已有
│
└─ 薪資扣繳方式             ← 只需要補這個
      ├─ 1 = 依扣繳稅額表
      └─ 2 = 固定 5%
```

然後 Payroll 自己做：

```text
當月應稅薪資
      +
配偶／扶養親屬人數
      +
扣繳方式
      ↓
當年度政府扣繳規定
      ↓
應扣所得稅
```

例如員工選「依扣繳稅額表」：

```text
當月薪資
    ↓
取得扶養資料
    ↓
查 2026 年薪資所得扣繳稅額表
    ↓
找到對應級距
    ↓
所得稅扣繳額
    ↓
薪資扣除
```

而且財政部的扣繳表本來就是按照「每月薪資所得 × 配偶及受扶養親屬人數」編製的。citeturn0search1

### 還要注意「一般月薪」和「非每月薪資」不同

例如獎金、津貼、補助等**非每月給付薪資**，目前規則原則上是另外按 5% 處理，而且有免扣繳門檻，不是直接跟月薪合併查同一張表。citeturn0search3

所以我們的薪資項目其實需要知道：

```text
薪資項目
├─ 是否屬於薪資所得
└─ 給付性質
   ├─ 每月給付
   └─ 非每月給付
```

這個會直接影響所得稅扣繳。

---

因此我會**撤回前面「另外做員工稅務設定模組」的建議**。

我們現在比較乾淨：

```text
人事資料
├─ 配偶
└─ 扶養親屬
        │
        ▼
薪資資料
├─ 扣繳方式
└─ 薪資項目給付性質
        │
        ▼
政府法規資料
└─ 當年度薪資所得扣繳稅額表
        │
        ▼
薪資結算
└─ 自動計算所得稅扣繳
```

這樣就夠了。

而且這符合我們目前整套系統的設計哲學：**既有資料能推導的就不要重複存，政府規則由法規模組提供，Payroll 負責實際計算。**

## 2026/08/23 09:46:00

### 使用者

所以扣繳方式有分經常性薪資扣繳跟非經常性薪資扣繳

### 助理

對，但要把兩個概念分開：

**不是「員工選擇經常性或非經常性扣繳」**，而是每一筆薪資給付本身會被判定為哪一種性質。

例如：

```text
薪資所得
├─ 經常性／每月給付薪資
│  ├─ 本薪
│  ├─ 固定津貼
│  └─ 其他每月固定給付
│
└─ 非經常性／非每月給付薪資
   ├─ 年終獎金
   ├─ 績效獎金
   ├─ 特定一次性獎金
   └─ 其他非每月給付
```

然後兩條扣繳路徑不同。

經常性薪資通常走：

```text
當月經常性薪資
      ↓
員工選擇的扣繳方式
      ├─ 薪資所得扣繳稅額表
      │      ↓
      │  配偶＋扶養人數
      │      ↓
      │  查當年度扣繳表
      │
      └─ 按全月給付總額 5%
```

而非每月給付的薪資，像獎金等，則依「非每月給付薪資」的扣繳規定處理，並不是拿扶養人數去查每月薪資扣繳表。財政部目前的扣繳規則確實把這兩種情況分開處理。citeturn0search0

所以這反而證明我們前面設計的**薪資項目**需要多一個很重要的屬性：

```text
薪資項目
├─ 是否屬於應稅薪資所得
└─ 扣繳給付性質
   ├─ 1 = 每月給付薪資
   └─ 2 = 非每月給付薪資
```

而「員工」本身只需要記：

```text
員工
├─ 配偶／扶養資料        ← 我們已經有
└─ 每月薪資扣繳方式
   ├─ 1 = 依薪資所得扣繳稅額表
   └─ 2 = 按全月薪資 5%
```

這樣 Payroll 才能自動判斷：

```text
                    薪資項目
                       │
              判斷給付性質
                 ┌─────┴─────┐
                 ▼           ▼
             每月給付      非每月給付
                 │           │
                 ▼           ▼
           員工扣繳方式    法定扣繳規則
                 │           │
                 └─────┬─────┘
                       ▼
                  所得稅扣繳
```

所以你說的沒錯，**經常性與非經常性應該是我們所得稅計算模型中的核心分類**；只是我不會把它設計成「員工選哪一種」，而是讓**薪資項目決定給付性質，員工只決定每月薪資採哪種扣繳方式**。

## 2026/08/23 09:47:27

### 使用者

一般經常性薪資不是都用依薪資所得扣繳稅額表  ??

### 助理

不是。**台灣目前規定不是「經常性薪資一律用薪資所得扣繳稅額表」**。

我剛重新查財政部 2026 年（民國 115 年）最新說明，對「我國境內居住者」的**每月給付薪資**，有兩種方式，原則上由納稅義務人選擇：citeturn0search0

```text
每月給付薪資
├─ 方式 1：依「薪資所得扣繳稅額表」
│          └─ 會用到配偶／受扶養親屬資料
│
└─ 方式 2：全月給付總額 × 5%
```

財政部的薪資所得扣繳稅額繳款書甚至直接分成「每月給付之薪資：選擇按扣繳稅額表」和「每月給付之薪資：選擇按 5% 扣繳」兩類。citeturn0search13

而另外一條才是：

```text
獎金、津貼、補助款等
非每月給付薪資／兼職所得
        ↓
原則按給付額 5%
        ↓
符合免扣繳門檻
        ↓
免予扣繳
```

2026 年財政部目前公布的非每月給付薪資免扣繳門檻為 **90,501 元**。citeturn0search1

所以對我們 HR 系統而言，我會修正成：

```text
員工
└─ 每月薪資扣繳方式
   ├─ 1 = 薪資所得扣繳稅額表
   └─ 2 = 5%

薪資項目
└─ 給付性質
   ├─ 每月給付
   └─ 非每月給付

                ↓

            薪資結算

每月給付
→ 看員工選擇的扣繳方式

非每月給付
→ 依政府當期非每月薪資扣繳規則
```

所以**我們確實還是需要在員工資料保存「每月薪資扣繳方式」**；單靠扶養資料還不夠。

不過不需要做成一整個「員工稅務模組」，增加一個扣繳方式設定即可。

## 建議調整 `employees`

我不建議把很多稅務欄位塞進 `employees`，只新增一個：

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `salary_withholding_method_code` | `int` | 必填 | 每月薪資所得扣繳方式。`1=依薪資所得扣繳稅額表`、`2=按全月給付總額5%` |

這個是**員工本人的扣繳選擇**。

它和：

```text id="taxflow"
扶養資料
```

一起提供 Payroll 使用。

# 扶養資料維持原本設計

因為我們之前已經建立扶養資料，所以不用再做一套「所得稅扶養資料」。

概念是：

```text id="dep-flow"
employee_dependents
├─ 姓名
├─ 身分證／識別資料
├─ 出生年月日
├─ 親屬關係代碼
├─ 是否列報扶養
├─ 生效日
└─ 結束日
```

薪資結算時：

```text id="taxcalc-flow"
employees.salary_withholding_method_code
            +
有效的扶養資料
            +
當月薪資所得
            +
當年度政府扣繳表
            ↓
         所得稅扣繳
```

---

# 但我建議扶養資料補一個很重要的概念

扶養人數不能永遠只看「目前有幾個」。

例如：

```text id="depend-history"
2026/01～06
扶養 2 人

2026/07～
扶養 3 人
```

如果我們回頭重算 2026 年 3 月薪資，不能拿現在的 3 人。

所以扶養資料最好具有：

```text id="dep-period"
effective_from
effective_to
```

這樣 Payroll 可以依**薪資期間當時有效的扶養資料**計算。

這和我們整套系統「歷史不能被現在設定覆蓋」的原則完全一致。

---

# 扣繳方式本身也有歷史問題

這點更重要。

如果：

```text id="withholding-change"
2026/01～06
依扣繳稅額表

2026/07～
改成 5%
```

如果只把：

```text id="current-value"
employees.salary_withholding_method_code = 2
```

那歷史會丟失。

所以我重新考慮後，**其實不建議把它直接放在 `employees` 當唯一欄位**。

更好的方式是：

```text id="withhold-setting"
employee_withholding_settings
```

### 用途說明

記錄員工每月薪資所得扣繳方式及其生效期間。

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 設定 ID |
| `employee_id` | `bigint` | 必填 | 員工 |
| `withholding_method_code` | `int` | 必填 | `1=薪資所得扣繳稅額表`、`2=5%` |
| `effective_from` | `date` | 必填 | 生效日 |
| `effective_to` | `date` | 選填 | 結束日 |
| `created_by` | `bigint` | 必填 | 建立／變更者 |
| `created_at` | `datetime` | 必填 | 建立時間 |

# 所以我會推薦這個版本

不是：

```text id="bad-emp"
employees
├─ 姓名
├─ 電話
├─ ...
├─ 扶養
├─ 所得稅方式
├─ 勞保
├─ 健保
├─ ...
```

而是：

```text id="clean-emp"
employees
├─ 員工基本資料
│
├─ employee_dependents
│  └─ 扶養資料＋有效期間
│
├─ employee_withholding_settings
│  └─ 每月薪資扣繳方式＋有效期間
│
├─ employee_employments
│  └─ 任職歷史
│
├─ employee_departments
│  └─ 部門歷史
│
└─ 其他人事關聯
```

這樣 Payroll 在算某一期薪資時，只要取：

```text id="payroll-input"
薪資期間
    ↓
當時有效的薪資
+
當時有效的扶養資料
+
當時有效的扣繳方式
+
當年度政府扣繳表
    ↓
所得稅
```

我認為這樣比「直接在 employees 加一個欄位」更符合我們整套 HR SaaS 的歷史追蹤設計。

兩者都保留歷史，薪資結算依**該薪資期間當時有效的設定**取得資料，不使用員工目前最新設定回算過去薪資。

這樣員工 Schema 的調整就確定了。
