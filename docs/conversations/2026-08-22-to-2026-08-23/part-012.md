在「薪資結算」畫面，不要讓使用者猜系統用了什麼法規。

例如：

```text
2026 年 8 月薪資結算

計算依據
━━━━━━━━━━━━━━━━━━━━

勞保
● 2026/01/01 版本

健保
● 2026/01/01 版本

勞退
● 2026/01/01 版本

職災
● 2025/01/01 版本

所得稅
● 2026/01/01 版本

          [開始結算]
```

甚至可以點開：

```text
為什麼這個員工的勞保是 1,xxx 元？

員工實際薪資
↓
投保薪資級距
↓
勞保費率
↓

↓

```

這會讓 HR **真的看得懂系統為什麼算出這個數字**。

---

所以我會把這個平台的 UI 原則定成一句話：

> **政府資料自動抓、HR 主要查看；公司設定由 HR 管理；薪資結算明確告訴 HR「這筆錢是依哪個版本、哪些規則算出來的」。**

這樣「法規設定」就不會變成一個很難用的技術管理後台，而是變成**薪資系統背後可靠的規則來源**。

# 1. `regulatory_sources`

## 用途說明

管理政府法規資料來源與同步設定。

例如：

- 勞動部
- 勞保局
- 健保署
- 財政部

這張不是法規內容，而是「去哪裡抓」。

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 資料來源 ID |
| `code` | `varchar(50)` | 必填 | 來源代碼 |
| `name` | `varchar(100)` | 必填 | 資料來源名稱 |
| `agency_name` | `varchar(100)` | 必填 | 政府機關名稱 |
| `dataset_code` | `varchar(100)` | 選填 | 政府開放資料集識別碼 |
| `api_url` | `varchar(1000)` | 必填 | API 位址 |
| `data_type_code` | `int` | 必填 | 資料類型，例如 JSON/XML/CSV |
| `sync_enabled` | `boolean` | 必填 | 是否啟用自動同步 |
| `last_synced_at` | `datetime` | 選填 | 最後成功同步時間 |
| `status_code` | `int` | 必填 | 來源狀態 |
| `created_at` | `datetime` | 必填 | 建立時間 |
| `updated_at` | `datetime` | 必填 | 更新時間 |

## 關聯

```text
regulatory_sources
        ↓
regulatory_datasets
```

## 設計理由

API URL、資料集代碼不要寫死在薪資程式裡。

政府更換 API 時，只調整來源設定。

# 3. `regulatory_dataset_versions`

## 用途說明

這張是法規歷史的核心。

每次政府公布新的適用版本，就產生一筆新的 Version。

例如：

```text
健保投保金額分級表
├─ 2025/01/01 版本
└─ 2026/01/01 版本
```

舊版本不能被新版本覆蓋。

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 法規資料版本 ID |
| `regulatory_dataset_id` | `bigint` | 必填 | 所屬資料集 |
| `version_code` | `varchar(50)` | 必填 | 版本代碼 |
| `effective_from` | `date` | 必填 | 適用開始日 |
| `effective_to` | `date` | 選填 | 適用結束日 |
| `source_published_at` | `datetime` | 選填 | 政府公布時間 |
| `synced_at` | `datetime` | 必填 | 系統同步時間 |
| `record_count` | `int` | 必填 | 本版本資料筆數 |
| `raw_data` | `json` | 必填 | 政府原始資料快照 |
| `checksum` | `varchar(128)` | 選填 | 原始資料校驗值 |
| `status_code` | `int` | 必填 | 版本狀態 |
| `created_at` | `datetime` | 必填 | 建立時間 |

## 設計理由

這張有兩個用途。

第一個是：

> **保存政府當時到底給了什麼。**

第二個是：

> 薪資結算可以明確知道自己使用哪個版本。

所以 `raw_data` 我會保留。

但是薪資計算不直接讀這坨 JSON。

# 4. `regulatory_records`

## 用途說明

保存政府資料經過解析後，可以直接給薪資系統使用的「標準化資料」。

這張是我認為這套設計裡最關鍵的一張。

例如同一張表可以保存：

```text
勞保級距
健保級距
勞退級距
職災行業別
費率
最低工資
```

但不靠大量 nullable 欄位硬塞，而是：

> 一筆 Record = 某個版本裡的一筆政府資料。

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 法規資料 ID |
| `dataset_version_id` | `bigint` | 必填 | 所屬法規版本 |
| `record_key` | `varchar(100)` | 必填 | 該筆資料唯一識別 |
| `code` | `varchar(100)` | 選填 | 政府代碼／級距代碼 |
| `name` | `varchar(200)` | 選填 | 名稱 |
| `value_from` | `decimal(18,4)` | 選填 | 區間起始值 |
| `value_to` | `decimal(18,4)` | 選填 | 區間結束值 |
| `value_amount` | `decimal(18,4)` | 選填 | 金額值 |
| `value_rate` | `decimal(18,8)` | 選填 | 費率 |
| `data` | `json` | 必填 | 該筆標準化後完整資料 |
| `sort_order` | `int` | 選填 | 級距／項目順序 |
| `created_at` | `datetime` | 必填 | 建立時間 |

## 設計理由

我們前面已經確認政府資料格式不一致。

例如：

```text
勞保
→ 月薪資總額
→ 投保薪資

職災
→ 行業類別
→ 行業別費率
→ 上下班費率

健保
→ 實際薪資月額
→ 投保金額
```

所以完全一表一種政府格式會拆得非常多。

全部 JSON 又會讓薪資難算。

因此這張採：

```text
常用共同數值 → 結構化欄位
特殊內容     → data JSON
```

取得平衡。

# 5. `regulatory_sync_logs`

## 用途說明

就是我們 UI 上看到的：

> 法規同步紀錄。

例如：

```text
2026/08/23 08:00
勞保局
同步成功

2026/08/23 08:02
健保署
同步失敗
API Timeout
```

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 同步紀錄 ID |
| `regulatory_dataset_id` | `bigint` | 必填 | 同步哪個資料集 |
| `started_at` | `datetime` | 必填 | 開始時間 |
| `finished_at` | `datetime` | 選填 | 完成時間 |
| `status_code` | `int` | 必填 | `1=進行中`、`2=成功`、`3=失敗`、`4=無異動` |
| `records_received` | `int` | 選填 | API 取得筆數 |
| `records_saved` | `int` | 選填 | 實際寫入筆數 |
| `new_version_id` | `bigint` | 選填 | 若產生新版本，記錄版本 ID |
| `error_message` | `text` | 選填 | 錯誤資訊 |
| `trigger_type_code` | `int` | 必填 | `1=自動`、`2=人工立即同步` |
| `created_at` | `datetime` | 必填 | 建立時間 |

## 設計理由

政府 API 掛掉不能影響現有薪資計算。

所以：

```text
同步失敗
↓
記錄失敗
↓
繼續使用目前有效法規版本
```

而不是把舊資料清掉。

# 6. `company_regulatory_settings`

## 用途說明

這張才是**公司可以操作的法規相關設定**。

也就是你一開始講的：

- 職災行業別
- 投保單位類別

以及未來真正屬於「這家公司」的投保基本設定。

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | 公司法規設定 ID |
| `company_id` | `bigint` | 必填 | 公司 ID |
| `insurance_unit_type_code` | `varchar(30)` | 必填 | 投保單位類別代碼 |
| `occupational_industry_code` | `varchar(30)` | 必填 | 職災行業別代碼 |
| `effective_from` | `date` | 必填 | 設定生效日 |
| `effective_to` | `date` | 選填 | 設定結束日 |
| `created_by` | `bigint` | 必填 | 設定者 |
| `created_at` | `datetime` | 必填 | 建立時間 |
| `updated_at` | `datetime` | 必填 | 更新時間 |

## 設計理由

這張和政府資料是兩回事。

例如政府資料：

```text
42
電腦程式設計、諮詢及相關服務業
職災費率 X
```

公司只記：

```text
本公司：
occupational_industry_code = 42
```

計算薪資時才：

```text
公司設定
↓
code = 42
↓
找當期政府職災版本
↓
找到 42 的費率
↓
計算
```

這樣政府未來改費率，不需要修改公司設定。

# 7. `payroll_regulatory_snapshots`

## 用途說明

這張負責實現我們最重要的原則：

> **薪資結算後，永遠知道當時使用哪一套政府法規。**

| 欄位 | 型態 | 必要性 | 說明 |
|---|---|---:|---|
| `id` | `bigint` | 必填 | Snapshot ID |
| `payroll_id` | `bigint` | 必填 | 薪資單 |
| `dataset_version_id` | `bigint` | 必填 | 使用的政府法規版本 |

# 因此我會修正我們法規模組的技術架構

不要做「網站爬蟲」。

而是做 **Provider Adapter**：

```text
                  法規同步服務
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     勞動部 Adapter  健保署 Adapter  其他 Adapter
          │            │
          ▼            ▼
      Dataset       Dataset
          │            │
          ▼            ▼
      Metadata       Metadata
          │            │
          ▼            ▼
      Resource       Resource
          └──────┬─────┘
                 ▼
             下載資料
                 ▼
             格式驗證
                 ▼
             內容比對
                 ▼
        ┌────────┴────────┐
        │                 │
      沒變               有變
        │                 │
       結束               ▼
                         新版本
                           │
                           ▼
                       法規歷史
```

### 所以我們現在可以正式定一個原則

**不要在 Schema 保存「永遠固定的 API 資料網址」。**

保存的是：

```text
政府來源
+
Dataset 識別資訊
+
同步 Adapter 類型
```

每次同步時，由 Adapter 去政府 API 找**目前真正的 Resource**。

當次實際使用的：

```text
resourceID
resource URL
抓取時間
checksum
```

再記錄到**同步／版本歷史**。

這樣即使 Resource URL 改變，也不影響我們。

---

還有一點很重要：**所得稅先不要硬塞進這套自動同步模型。**等我們正式設計所得稅計算時，再確認財政部當年度扣繳表實際提供的機器可讀格式與更新方式。

所以目前可以很有把握地把**勞保／就保、職災、勞退、健保**先納入自動法規同步架構；這個技術方向是可行的。
