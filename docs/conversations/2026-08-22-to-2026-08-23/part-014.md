## 為什麼還需要這張？

因為 `raw_data` 是：

> 政府原封不動給我們的東西。

`regulatory_records` 是：

> 我們整理成 Payroll 看得懂的東西。

例如政府可能給：

```text
{
    "投保薪資等級": "第12級",
    "月薪資總額": "42001-45800",
    "月投保薪資": "45800"
}
```

我們解析成：

```text
code       = 12
range_from = 42001
range_to   = 45800
amount     = 45800
```

Payroll 就可以直接：

```text
薪資 45,000
    ↓
42,001 ～ 45,800
    ↓
投保薪資 45,800
```

不需要每次算薪資都重新解析政府 JSON。

## 2026/08/23 10:08:31

### 使用者

這版本看起來沒問題，你思考看看是否還有沒想到的問題

### 助理

有，我再從「**同步可靠性、歷史版本、Payroll 使用、安全性、SaaS 多公司**」幾個角度重新壓一次。這版沒有需要推翻，但我看到 **7 個邊界問題**，其中 4 個我建議現在就定。

1. **政府資料變更不一定代表「新法規版本」**。例如政府只是修正錯字、排序或 API 格式，checksum 會變，但實際計算內容可能沒變。所以同步流程最好分成：

```text
抓到新資料
↓
checksum 不同
↓
解析
↓
比較「標準化後的計算資料」
├─ 計算內容沒變 → 只記同步紀錄
└─ 計算內容有變 → 建立新法規版本
```

我建議採這個，不然可能產生很多假版本。

2. **`effective_from` 不一定政府資料都直接提供**。有些資料會明確寫「115/1/1 起適用」，有些可能只有公告日期或版本名稱。這種情況不要讓系統猜日期。應該：

```text
政府明確提供適用日 → 自動建立
沒有明確適用日 → 標記待確認
```

未確認前不能自動成為 Payroll 有效版本。這個我認為一定要有。

3. **新版本不能一抓到就立刻取代舊版本**。即使資料解析成功，也可能政府資料異常。所以我建議版本狀態至少有：

```text
1 = 待驗證
2 = 有效
3 = 已取代
4 = 無效
```

流程：

```text
政府更新
↓
建立待驗證版本
↓
格式、筆數、區間、重複值等檢查
↓
通過
↓
才正式啟用
```

是否要完全自動從「待驗證 → 有效」，可以依資料來源決定。

4. **同一類法規的有效期間不能重疊**。例如：

```text
健保級距 A
2026/01/01～2026/12/31

健保級距 B
2026/07/01～2027/06/30   ❌
```

這樣 2026/8 Payroll 不知道用哪個。所以同一 `dataset_code` 的有效版本原則上不能有重疊期間。

5. **公司投保設定也可能需要未來生效設定**。例如 HR 8/20 設定：

```text
目前職災行業別：42

9/1 起：
改成 43
```

這和我們公司贈與的概念一樣，因此 `company_regulatory_settings` 用有效期間是正確的，而且要防止同一公司期間重疊。

6. **多公司 SaaS 的政府法規資料不需要每家公司各存一份**。這一點很重要。

```text
政府法規資料
→ 全平台共用

公司投保設定
→ 每家公司自己的
```

所以：

```text
regulatory_dataset_versions
regulatory_records
regulatory_sync_logs
```

應該是平台層級資料，不帶 `company_id`。

只有：

```text
company_regulatory_settings
```

才帶公司。

這樣 N 家公司不用各自同步一份健保級距。

7. **Payroll 最後還是要 Snapshot**。現在這 4 張表負責的是「法規資料來源」，但薪資真正結算時還需要記：

```text
這次 Payroll
用了哪個勞保版本
用了哪個健保版本
用了哪個職災版本
用了哪個所得稅版本
```

不一定現在就要把 Payroll Snapshot Schema 加進法規模組，但需求一定要保留。

---

我現在會把這一版核心整理成：

```text
法規設定
├─ 公司投保設定
│  ├─ 職災行業別
│  ├─ 投保單位類別
│  └─ 生效歷史
│
├─ 政府法規版本
│  ├─ 適用期間
│  ├─ 政府原始資料
│  ├─ 待驗證／有效／失效
│  └─ 歷史版本
│
├─ 法規計算資料
│  └─ Payroll 可直接使用的標準化資料
│
└─ 同步紀錄
   ├─ 自動同步
   ├─ 人工同步
   ├─ 無異動
   └─ 失敗
```

我最建議你現在確認的是 **1、2、3、4**：  
**資料有變不等於法規有變、沒有適用日不能猜、新版本先驗證、有效期間不能重疊。**

這四條定下來後，這個法規同步模組就會穩很多。

對，你這樣講比較合理。**我上一輪把「人工確認」設計得太保守了。**

既然我們抓的是政府已經正式發布、而且資料本身能辨識「適用版本／適用年度／生效日」的結構化資料，那就不需要 HR 每次人工判斷。

```text
政府資料同步
    ↓
發現新 Resource / 資料內容改變
    ↓
抓取資料
    ↓
解析資料
    ↓
取得政府提供的
├─ 版本／年度
├─ 生效日期
└─ 資料內容
    ↓
系統自動驗證
├─ 格式正確？
├─ 必要欄位都有？
├─ 級距合理？
├─ 有沒有重複？
├─ 版本是否已存在？
└─ 資料是否完整？
    ↓
驗證成功
    ↓
建立「未來／目前有效」法規版本
```

### 關鍵是「抓到新版本」跟「立即使用」是兩回事

例如今天是 2026/11/20，政府已經公布：

```text
2027 年健保投保金額分級表
生效日：2027/01/01
```

系統今天就可以抓進來：

```text
2026版本
effective_from = 2026/01/01
effective_to   = 2026/12/31

2027版本
effective_from = 2027/01/01
effective_to   = NULL
```

但 Payroll 在算：

```text
2026/12 薪資
→ 自動使用 2026 版本

2027/01 薪資
→ 自動使用 2027 版本
```

所以不是：

> 抓到 2027 → 馬上把 2026 換掉 ❌

而是：

> 抓到 2027 → 先存起來 → 到適用期間自動使用。 ✅

這樣其實**根本不需要一個「HR 按核准」流程**。

### 那 `status_code` 也可以簡化

我前面設：

```text
待驗證
有效
已取代
無效
```

其實有點多。

我們已經有：

```text
effective_from
effective_to
```

就可以判斷：

```text
尚未生效
目前有效
歷史版本
```

這三個其實是**計算出來的狀態**，不用存在資料庫。

例如今天：

```text
effective_from > 今天
→ 尚未生效

effective_from <= 今天
AND
effective_to >= 今天 / NULL
→ 目前有效

effective_to < 今天
→ 歷史版本
```

所以 `status_code` 甚至可以只負責：

```text
1 = 正常
2 = 無效
```

「無效」主要留給資料真的有問題、政府撤回、我們解析錯誤之類的特殊狀況。

所以我同意你這個修正。

我們這一塊的原則正式改成：

> **政府正式結構化資料只要能取得明確版本／生效資訊，系統自動抓、自動驗證、自動保存；不需要人工核准。Payroll 根據薪資適用日期自動選擇正確版本。**

只有一種情況才需要人介入：

```text

政府資料缺欄位
無法解析版本／生效日

```
