### 為什麼放公司設定？

因為：

**職災行業別**

是「這家公司／投保單位」的屬性，不是某個員工的個人屬性。

它會影響：

```text id="u5x3ke"
公司
 ↓
職災費率／相關規則
 ↓
員工投保
 ↓
公司負擔成本
```

同樣地：

**投保單位類別**

也是投保單位層級的設定。

所以不應該變成：

```text id="x8b0p2"
employees.職災行業別 ❌
employees.投保單位類別 ❌
```

而是：

```text id="b8y3nq"
公司基本設定
      ↓
投保單位設定
      ↓
員工投保資料
      ↓
勞保／健保／就保／勞退計算
      ↓
薪資結算
      ↓
人事成本
```

### 但有一個地方要注意

**不要把「公司設定」跟「員工投保資料」混在一起。**

例如：

```text id="x0e6d3"
公司層級
├─ 投保單位類別
├─ 職災行業別
└─ 投保單位相關設定

├─ 勞保投保
├─ 健保投保
├─ 就保
├─ 勞退
└─ 個人投保級距
```

這樣才合理。

### 這三個模組的責任要分清楚

#### ① 系統設定

回答：

> **「誰可以做什麼？」**

例如：

```text id="3c0qba"

├─ HR
├─ 薪資人員
├─ 部門主管
└─ 一般員工

├─ 查看員工
├─ 修改員工
├─ 核准請假
├─ 核准加班
├─ 核發補休
├─ 核發薪資
└─ 查看薪資
```

---

#### ② 法規設定

回答：

> **「政府規定怎麼算？」**

例如：

```text id="0q1jvt"
法規設定
     ↓
薪資計算
     ↓
勞保／就保
     ↓
健保
     ↓
勞退
     ↓
職災
```

而且這裡最重要的是：

> **法規一定要有版本與生效日期。**

例如：

```text id="m0t5h8"
法規 A
2026/01/01 ～ 2026/12/31

法規 B
2027/01/01 ～ 未來
```

這樣歷史薪資才不會因為政府改規定而被重新計算。

---

#### ③ 稽核日誌

回答：

> **「誰在什麼時間，對什麼資料做了什麼？」**

例如：

```text id="5s3v0u"
王小明
2026/08/22 10:32
核准員工 A 的特休

↓
留下稽核紀錄
```

甚至：

```text id="f8r2lp"
修改前
基本薪資 = 35,000

修改後
基本薪資 = 38,000

操作者
HR001

時間
2026/08/22 11:15
```

這對我們前面設計的：

- 薪資
- 補休
- 請假
- 打卡撤銷
- 補登
- 公司贈與假
- 核發
- 撤銷

都非常重要。

# 二、Schema ① `regulatory_settings`

### 用途

系統目前採用的**公司／投保單位法規基本設定**。

這就是你剛才截圖裡面的：

- 職災行業別
- 投保單位類別

主要放這裡。

### 欄位

| 欄位 | 型態 | 必要 | 說明 |
|---|---|---:|---|
| `id` | BIGINT | ✓ | 主鍵 |
| `occupational_industry_code` | VARCHAR(20) | ✓ | 職災行業別代碼，例如 42 |
| `insurance_unit_type_code` | VARCHAR(20) | ✓ | 投保單位類別 |
| `effective_date` | DATE | ✓ | 設定生效日期 |
| `end_date` | DATE | | 設定結束日期 |
| `created_at` | TIMESTAMP | ✓ | 建立時間 |
| `updated_at` | TIMESTAMP | ✓ | 修改時間 |

### 設計理由

這裡只放：

> **「這家公司是什麼投保單位、屬於什麼職災行業」**

不要把：

- 勞保費率
- 健保費率
- 勞退比例
- 最低工資

直接塞進來。

因為那些是**政府規則**，不是公司的固定屬性。

# 四、Schema ③ `regulatory_rule_versions`

這張其實是**整個法規模組最重要的表**。

### 用途

同一條規則會因為政府修改而產生不同版本。

例如：

```text
最低工資
├─ 2025 版本
├─ 2026 版本
└─ 2027 版本
```

不能直接修改原本資料。

### 欄位

| 欄位 | 型態 | 必要 | 說明 |
|---|---|---:|---|
| `id` | BIGINT | ✓ | 主鍵 |
| `regulatory_rule_id` | BIGINT | ✓ | 所屬法規規則 |
| `version` | VARCHAR(30) | ✓ | 規則版本 |
| `effective_from` | DATE | ✓ | 生效日 |

# 五、為什麼 `rule_definition` 用 JSONB？

因為政府規則不是全部都是單純一個數字。

例如某些規則可能是：

```text
基本比例
+ 級距
+ 上限
+ 下限
+ 特定條件
+ 特定日期
```

如果全部硬塞成：

```text
rate
amount
min
max
```

很快就會不夠用。

所以可以：

```text
rule_definition
```

保存該版本的計算參數。

例如概念上：

```text
{
    "rate": 0.05,
    "min": 29500,
    "max": 458000,
    "calculation": "..."
}
```

**但真正的計算邏輯不要全部放 JSON。**

JSONB 適合放：

> 規則參數

而計算引擎負責：

> 怎麼計算。

這個界線很重要。

## 我會特別定下這 4 個原則

**① 公司設定 ≠ 法規規則**

公司選擇自己的職災行業別、投保單位類別；政府規則則另外管理。

**② 法規一定版本化**

**③ 法規參數 ≠ 計算程式**

**④ 薪資結算必須留下使用哪個法規版本**
