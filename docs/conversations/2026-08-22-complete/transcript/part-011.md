### 為什麼放公司設定？

因為：

**職災行業別**

是「這家公司／投保單位」的屬性，不是某個員工的個人屬性。

它會影響：

```text id="u5x3ke"
公司
 ↓
職災費率／相關規則
 ↓
員工投保
 ↓
公司負擔成本
```

同樣地：

**投保單位類別**

也是投保單位層級的設定。

所以不應該變成：

```text id="x8b0p2"
employees.職災行業別 ❌
employees.投保單位類別 ❌
```

而是：

```text id="b8y3nq"
公司基本設定
      ↓
投保單位設定
      ↓
員工投保資料
      ↓
勞保／健保／就保／勞退計算
      ↓
薪資結算
      ↓
人事成本
```

# 二、Schema ① `regulatory_settings`

### 用途

系統目前採用的**公司／投保單位法規基本設定**。

這就是你剛才截圖裡面的：

- 職災行業別
- 投保單位類別

主要放這裡。

### 欄位

| 欄位 | 型態 | 必要 | 說明 |
|---|---|---:|---|
| `id` | BIGINT | ✓ | 主鍵 |
| `occupational_industry_code` | VARCHAR(20) | ✓ | 職災行業別代碼，例如 42 |
| `insurance_unit_type_code` | VARCHAR(20) | ✓ | 投保單位類別 |
| `effective_date` | DATE | ✓ | 設定生效日期 |
| `end_date` | DATE | | 設定結束日期 |
| `created_at` | TIMESTAMP | ✓ | 建立時間 |
| `updated_at` | TIMESTAMP | ✓ | 修改時間 |

### 設計理由

這裡只放：

> **「這家公司是什麼投保單位、屬於什麼職災行業」**

不要把：

- 勞保費率
- 健保費率
- 勞退比例
- 最低工資

直接塞進來。

因為那些是**政府規則**，不是公司的固定屬性。

# 四、Schema ③ `regulatory_rule_versions`

這張其實是**整個法規模組最重要的表**。

### 用途

# 五、為什麼 `rule_definition` 用 JSONB？

因為政府規則不是全部都是單純一個數字。

例如某些規則可能是：

```text
基本比例
+ 級距
+ 上限
+ 下限
+ 特定條件
+ 特定日期
```

如果全部硬塞成：

```text
rate
amount
min
max
```

很快就會不夠用。

所以可以：

```text
rule_definition
```

保存該版本的計算參數。

例如概念上：

```text
{
    "rate": 0.05,
    "min": 29500,
    "max": 458000,
    "calculation": "..."
}
```

**但真正的計算邏輯不要全部放 JSON。**

JSONB 適合放：

> 規則參數

而計算引擎負責：

> 怎麼計算。

這個界線很重要。

```text
              ┌──────────────┐

政府法規 ───────→ 法規規則
                     │
                     ▼
              法規規則版本
                     │
                     ▼
              法規參數
                     │
                     ▼
              薪資計算引擎
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      薪資          加班          請假
        │            │            │
        └────────────┼────────────┘
                     ▼

```

## 我會特別定下這 4 個原則

**① 公司設定 ≠ 法規規則**

公司選擇自己的職災行業別、投保單位類別；政府規則則另外管理。

**② 法規一定版本化**

不能直接修改舊規則，否則歷史薪資會被影響。

**③ 法規參數 ≠ 計算程式**

資料庫保存「政府規定的數值與條件」，程式負責執行計算。

**④ 薪資結算必須留下使用哪個法規版本**

例如 2026 年 8 月薪資結算使用 `2026` 版本。即使 2027 年政府改規定，**2026 年已結算的資料仍然知道當時用的是哪套規則。**

這樣這個「法規設定」就能真正成為我們後面**薪資計算引擎的規則來源**，而不是單純存幾個勞健保欄位。

### 1. `regulatory_settings`

這是**公司自己的設定**。

例如現在公司：

```text
職災行業別：
42 電腦程式設計、諮詢及相關服務業

投保單位類別：
公民營事業、機構
```

如果公司未來改變，也要留下歷史。

---

### 2. `regulatory_rules`

這是定義「我們系統有哪些法規規則」。

例如：

```text
最低工資
勞保費
健保費
勞退
職災
平日加班費
休息日加班費
特休未休工資
所得稅
```

這張比較像**規則目錄**，不是放每一年的數值。

---

### 3. `regulatory_rule_versions`

真正保存歷史。

例如：

```text
最低工資
│
├─ 2025 版本
│   生效：2025/01/01
│   最低月薪：28,590
│
├─ 2026 版本
│   生效：2026/01/01
│   最低月薪：29,500
│
└─ 2027 版本
    生效：2027/01/01
    ...
```

這樣薪資結算時：

```text
薪資結算日期
      ↓
找當時有效的法規版本
      ↓
依該版本計算
      ↓
保存結算結果
```

### 最重要的是這個

假設：

```text
2026 年 8 月薪資
→ 使用 2026 法規版本
→ 已結算
```

到了 2027 年政府改規定：

```text
2027 法規版本
```

**不能回頭改掉 2026 的法規版本。**

所以即使未來重新查看：

> 「2026 年 8 月這個員工的薪資為什麼是這個數字？」

系統還是能找到當時使用的法規。
