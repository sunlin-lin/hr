### 2. 員工在生效日前離職

例如：

```text

```


```text

```

### 3. 同一批次可以混不同假別嗎？

例如同一批：

```text
2026 年福利
```

裡面：

```text

員工 B → 福利假 8h
員工 C → 補休 4h
```

技術上可以，但我**不建議**。

我比較建議：

> **一個贈與批次只對應一種假別、薪資類型、額度及有效期間。**

例如：

```text
批次 A

特休 / 有薪 / 8h / 9~12月

批次 B
2026 專案福利假
福利假 / 有薪 / 8h / 9~12月
```

這樣批次的意義非常清楚。

---

### 4. 批次核發是否要「全部成功」？

> **採逐員工獨立核發，不因一個員工失敗而全部 rollback。**

# 本輪總結：公司贈與假別制度

## 一、核心概念

公司可以直接贈與員工假別額度。

**不是員工申請，也不是員工彼此轉贈。**

```text
有權限的人員
    ↓
建立公司贈與批次
    ↓
指定員工
    ↓
直接核發
    ↓
產生員工的假別額度
```

---

# 二、贈與批次

建立：

```text
company_leave_grant_batches
```

一個批次代表一次公司的贈與活動。

例如：

```text
2026 生日特休
```

一個批次：

- **不能混用不同假別**
- **不能混用不同薪資類型**
- 可以指定多名員工
- 個別員工核發失敗，不影響其他員工
- 失敗員工可以之後重新核發

例如：

```text
批次 A
────────────────
假別：特休
薪資：有薪
額度：8 小時
開始：2026/09/01
結束：2026/12/31

    ↓

員工 A → 成功
員工 B → 成功
員工 C → 失敗
員工 D → 成功
```

C 可以單獨重新核發。

# 四、假別

這一點已經明確：

```text
特休 ≠ 福利假 ≠ 補休
```

也就是：

- 公司贈與特休 → **就是特休**
- 公司贈與福利假 → **就是福利假**
- 公司贈與補休 → **就是補休**

不把福利假併進特休。

而特休、補休會進入各自的額度系統。

---

# 五、有薪／無薪

公司贈與一定要記錄：

```text
pay_type_code
```

只有兩種：

```text
1 = 有薪
2 = 無薪
```

而且這個值是在**核發時決定**。

後續產生實際額度時保留 Snapshot。

請假申請本身不再重複存一份 `pay_type_code`，避免資料不一致。

---

# 六、開始日與結束日

公司贈與必須指定：

```text
effective_from
effective_to
```

**兩個都必填。**

而且：

```text
effective_to >= effective_from
```

例如：

```text
核發時間：2026/08/22

可使用期間：
2026/09/01 ～ 2026/12/31
```

因此：

> **核發時間 ≠ 生效時間**

可以提前核發，但尚未到生效日之前不能使用。

---

# 七、核發後不能修改

核發完成後：

```text
granted_minutes
effective_from
effective_to
```

都不能直接修改。

例如：

```text
原本：
8 小時
09/01～12/31
```

不能直接 UPDATE 成：

```text
4 小時
09/01～10/31
```

需要透過既定的撤銷／調整機制處理，原始歷史必須保留。

---

# 八、撤銷

### 尚未生效

可以撤銷。

例如：

```text
8/22 核發
9/1 生效
8/25 發現錯誤
```

可以撤銷。

### 已經使用

已使用的部分不能被原始撤銷動作抹掉。

原始贈與紀錄仍然保留，已使用歷史也保留。

---

# 九、到期

到：

```text
effective_to
```

之後：

```text
額度仍存在
        ↓
自動判定不可使用
        ↓
不刪除
        ↓
歷史保留
```

因此未來仍然能查：

```text

已使用多少
剩餘多少
何時到期
```

# 十五、整體設計原則

這一輪其實確定了一個很重要的架構：

> **原始事實、額度、使用紀錄、薪資結算分開。**

也就是：

```text

        ↓
```

- 額度到期
- 贈與撤銷
- 請假撤銷

都不會破壞過去的歷史資料。

# 十六、額度不要用「直接 UPDATE」當帳務

然後不知道為什麼少了 8。

```text

    ↓

    ↓

    ↓
```

最後算出：

```text
可用額度
```

這樣才能做稽核。

# 五、④ 到職／離職

# 八、⑥ 班表／排班

這是出勤的上游。

我們已經討論到班表必須支援：

- 一般週休
- 輪班
- 做二休二
- 零工
- 不固定班
- 假日上班
- 調班
- 員工請假

核心概念不能只是：

```text id="xczv6w"
Monday = 上班
Tuesday = 上班
```

因為：

> 一週永遠只有 7 天，但「做二休二」是週期，不是星期制度。

因此我們討論的方向是：

```text id="7r7w8t"
schedule_templates
        ↓
schedule_periods / roster
        ↓
employee_schedules
```

# 九、班表與員工

```text

    ↓

```

`employee_schedules` 是：

> 某一個員工在某一天實際被排什麼班。

而不是永久規則。

例如：

```text id="b8s3ye"

員工 A
09:00～18:00
```

# 十、調班

我們也討論過：

> 班已經排好了，中途調班怎麼辦？

```text id="a9p3sv"

    ↓
調班
    ↓
```

必須保留歷史。

不能直接把過去的排班改掉而完全沒有紀錄。

# 十一、⑦ 出勤／打卡

```text id="n7j6l2"
   ↓
```

# 十二、打卡撤銷

我們已經確定：

> 上班、下班打卡都可以撤銷。

所以不能把打卡紀錄直接 DELETE。

應該：

```text id="c2mx7r"
attendance_record
      ↓

      ↓
保留原始紀錄
```

# 十三、補登打卡

```text id="r2x3nn"

```

而且我們特別決定：

例如：

```text id="3w5zaf"

→ 補登上班

忘記下班打卡
→ 補登下班
```

不是一定要一次補完整天。

# 十四、GPS

所以：


# 十五、⑧ 加班

我們已經討論：

> 只有班表定義「這天原本是休假／假日上班」的人，才具備申請加班的條件。

所以：

```text id="e4m9si"
employee_schedule
        ↓
判定當日班別
        ↓
是否允許申請加班
```

而加班之後有兩種主要去向：

```text id="5qqfco"
加班
 ├──→ 加班費
 │
 └──→ 補休
```

# 十六、⑨ 補休

補休是請假系統與加班系統的交界。

來源可以是：

```text id="y3s9tp"
加班
公司贈與
人工調整
```

產生：

```text id="7fljwl"
compensatory_leave_credits
```

而補休使用：

```text id="9cgrs8"
compensatory_leave_credits
       ↓
leave_request_allocations
```

---

# 十七、補休特殊規則

我們已經確定：

> 加班不一定換錢，也可以換補休。

而：

> 補休到期沒有使用完，必須轉成薪資。

另外我們特別討論過：

> 補休核發當下要由核發者選擇「基準值」。

而且：

> **結算後不能異動。**

所以未來薪資計算不能重新拿「現在的薪資」倒算以前的補休。

必須使用：

```text id="qdrbvn"
補休核發時的 Snapshot
```

我們已經把這部分完整定案。

# 二十八、⑬ 人事成本

因此部門歷史會影響成本歸屬。

### 使用者

薪資結算的部分應該還缺少政府的計算規定

### 助理

對，你這個提醒是對的。**「薪資結算」目前確實少了一整層「政府／法規計算規則」**。

而且我會建議不要把它簡化成「勞基法」，因為實際薪資結算會同時受到最低工資、加班費、勞健保、勞退、所得稅等規定影響。勞動部目前也明確要求薪資明細要能呈現各項工資、扣除項目及實際發給金額。citeturn0search0turn0search7

所以我們的總體應該修正成：

```text
薪資結算 🟡
├─ 政府／法規計算規定
│  ├─ 最低工資
│  ├─ 正常工時規定
│  ├─ 加班費計算規定
│  ├─ 休息日出勤計算
│  ├─ 例假出勤計算
│  ├─ 國定假日出勤計算
│  ├─ 特別休假未休工資
│  ├─ 平均工資計算
│  ├─ 工資定義
│  ├─ 工資扣除規定
│  ├─ 勞保／就保相關計算
│  ├─ 健保相關計算
│  ├─ 勞退提繳
│  ├─ 所得稅／扣繳
│  └─ 法規版本／生效日期
│
├─ 員工薪資資料
├─ 薪資項目
├─ 出勤資料
├─ 請假資料
├─ 加班資料
├─ 補休資料
├─ 法定扣款
├─ 公司代扣項目
├─ 薪資計算
├─ 薪資審核
├─ 薪資核發
├─ 薪資明細
└─ 結算後 Snapshot
```

### 而且這裡有一個很重要的設計

**政府規定不能直接寫死在程式碼裡。**

例如目前最低工資自 2026 年起為月薪 29,500 元、時薪 196 元；加班費又有不同時數與日別的計算規則。citeturn0search2turn0search3

所以我們後面應該設計成：

```text
政府計算規定
      ↓
規則版本
      ↓
生效日期
      ↓
薪資計算引擎
      ↓
員工當期薪資
```

例如：

```text
2026/01/01
最低工資規則 V2026
        ↓
2026 年薪資計算

2027/01/01
最低工資規則 V2027
        ↓
2027 年薪資計算
```

這樣未來政府調整規定，**不能重新計算過去已結算的薪資**。

這跟我們前面「補休核發時基準值固定、結算後不能異動」的設計理念是一致的。

另外，勞動部的規定也顯示，加班費不是單純「底薪 ÷ 240」，而是要依平日、休息日、例假、國定假日等不同情況計算；而且「工資」的認定也會影響加班費的計算基礎。citeturn0search2turn0search6

所以我會把這一塊提升成一個獨立的大子模組：

```text
薪資結算 🟡
├─ 政府／法規規則 ⭐
├─ 薪資計算
├─ 法定扣款
├─ 公司扣款
├─ 加班費
├─ 未休假工資
├─ 勞保／就保
├─ 健保
├─ 勞退
├─ 所得稅
├─ 薪資明細
├─ 薪資審核
├─ 薪資核發
└─ 歷史結算
```

**這個「政府／法規規則」我建議列為薪資模組的第一級核心，而不是附屬功能。**

而且它之後還會反過來依賴我們前面做的**班表、打卡、請假、加班、補休、薪資項目**，所以這也代表我們現在的整體架構方向是正確的。
